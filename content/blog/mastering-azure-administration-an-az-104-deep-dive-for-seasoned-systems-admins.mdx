# Mastering Azure Administration: An AZ-104 Deep Dive for Seasoned Systems Admins

In an IT landscape increasingly dominated by cloud computing, the role of a Systems Administrator has evolved dramatically. No longer confined to on-premises data centers, we're now architects and custodians of infrastructure spanning hybrid and multi-cloud environments. Microsoft Azure stands as a formidable player in this domain, offering a vast array of services that can either empower or overwhelm an organization.

For many experienced IT professionals, the Microsoft Certified: Azure Administrator Associate (AZ-104) certification is a crucial milestone. It validates your capability to implement, manage, and monitor an organization's Microsoft Azure environment. But beyond the exam, the true value lies in translating that knowledge into practical, robust, and cost-effective solutions.

As a Systems Administrator with a decade of experience navigating complex IT infrastructure, virtualization, automation, and cloud technologies, I've seen firsthand how foundational cloud skills directly impact operational efficiency and organizational agility. This "AZ-104 Masterclass" isn't just about passing an exam; it's about transforming your theoretical understanding into actionable administrative excellence. ### The Modern Admin's Toolkit: Why AZ-104 Matters

### 1. Managing Azure Identities and Governance: The Foundation of Control

Effective identity and access management (IAM) is paramount in any IT environment, and Azure is no exception. The AZ-104 emphasizes Azure Active Directory (Azure AD) – now Microsoft Entra ID – and its integration with traditional on-premises AD, as well as robust governance tools like Azure Policy and Role-Based Access Control (RBAC).

#### 1.1. Azure Active Directory (Microsoft Entra ID) Management

From creating users and groups to configuring multi-factor authentication (MFA) and conditional access, Entra ID is your command center for identity. For systems administrators, integrating with existing on-premises AD through Azure AD Connect is often a critical first step, establishing a hybrid identity model.

**Practical Tip:** Always enforce MFA. Seriously. It's the simplest yet most effective security measure you can deploy. Use Conditional Access policies to enforce specific access requirements based on user location, device state, or application.

**Code Example: Creating an Azure AD User and Group with Azure CLI**

```azurecli
# Create an Azure AD User
az ad user create --display-name "Randy DeRego" \
                  --password "StrongPassword123!" \
                  --user-principal-name "randy.derego@yourcompany.onmicrosoft.com" \
                  --force-change-password-next-login true

# Create an Azure AD Group
az ad group create --display-name "Azure_Admins" \
                   --mail-nickname "AzureAdmins" \
                   --description "Group for Azure Administrators"

# Add the user to the group
# First, get the object ID of the user and group
USER_OBJECT_ID=$(az ad user show --id "randy.derego@yourcompany.onmicrosoft.com" --query id --output tsv)
GROUP_OBJECT_ID=$(az ad group show --group "Azure_Admins" --query id --output tsv)

az ad group member add --group-id $GROUP_OBJECT_ID --member-id $USER_OBJECT_ID
```

#### 1.2. Role-Based Access Control (RBAC) and Azure Policy

RBAC defines *who* can do *what* on *which* resources. This granular control is crucial. For experienced admins, moving from NTFS permissions to RBAC requires a shift in mindset but offers vastly superior scalability and auditability. Azure Policy, on the other hand, enforces standards and compliance at scale, ensuring your environments adhere to organizational rules.

**Practical Tip:** Implement the principle of least privilege. Don't assign Contributor where Reader will suffice. Create custom RBAC roles for specific administrative tasks that don't fit into built-in roles, but only when absolutely necessary to avoid role sprawl. Use Azure Policy to enforce resource tagging, location restrictions, or ensure specific security configurations are applied to all resources.

**Code Example: Assigning an RBAC Role and Creating a Simple Azure Policy with Azure CLI**

```azurecli
# Assign the "Virtual Machine Contributor" role to the Azure_Admins group at the resource group scope
# First, get the resource group ID
RG_ID=$(az group show --name "my-production-rg" --query id --output tsv)

# Get the object ID of the Azure_Admins group
GROUP_OBJECT_ID=$(az ad group show --group "Azure_Admins" --query id --output tsv)

az role assignment create --assignee-object-id $GROUP_OBJECT_ID \
                          --role "Virtual Machine Contributor" \
                          --scope $RG_ID \
                          --assignee-principal-type Group

# Create a simple Azure Policy to restrict resource locations to "East US"
# Policy definition JSON (save as policyDefinition.json)
# {
#   "if": {
#     "not": {
#       "field": "location",
#       "in": [
#         "eastus",
#         "eastus2"
#       ]
#     }
#   },
#   "then": {
#     "effect": "deny"
#   }
# }

# Create the policy definition
az policy definition create --name "AllowedLocations" \
                            --display-name "Allowed Locations for Resources" \
                            --description "This policy ensures that resources are deployed only to East US or East US 2." \
                            --rules "./policyDefinition.json" \
                            --mode All

# Assign the policy to a subscription (or resource group)
SUBSCRIPTION_ID=$(az account show --query id --output tsv)
az policy assignment create --name "AllowedLocationsAssignment" \
                            --display-name "Enforce Allowed Locations" \
                            --scope "/subscriptions/$SUBSCRIPTION_ID" \
                            --policy "AllowedLocations"
```

### 2. Implementing and Managing Storage: Data Where You Need It, When You Need It

Storage is the bedrock of any application. Azure offers a comprehensive suite of storage solutions, each optimized for different workloads: Blob storage for unstructured data, File storage for SMB/NFS shares, Table storage for NoSQL, and Queue storage for messaging. For us admins, the challenge is not just provisioning storage but ensuring it's secure, cost-effective, and highly available.

#### 2.1. Azure Storage Accounts and Data Management

Understanding storage tiers (Hot, Cool, Archive), replication options (LRS, GRS, RA-GRS, ZRS, GZRS, RAGZRS), and access methods (shared access signatures, access keys) is fundamental. For migrating on-premises file servers, Azure Files with Azure File Sync is a game-changer.

**Practical Tip:** Always choose the right storage tier and replication strategy based on your data's access frequency, criticality, and recovery objectives. Don't pay for Hot storage if your data is rarely accessed (Archive is significantly cheaper). Leverage Azure File Sync for seamless hybrid file share management.

**Code Example: Creating a Storage Account and Uploading a Blob with Azure CLI**

```azurecli
# Define variables
STORAGE_ACCOUNT_NAME="yourcompanystorage$(head /dev/urandom | tr -dc a-z0-9 | head -c 8)" # Ensure globally unique
RESOURCE_GROUP_NAME="my-storage-rg"
LOCATION="eastus"
CONTAINER_NAME="backups"
FILE_TO_UPLOAD="local_backup.zip" # Assume you have this file locally

# Create a resource group if it doesn't exist
az group create --name $RESOURCE_GROUP_NAME --location $LOCATION

# Create a storage account with specific settings (Standard_LRS, Hot tier)
az storage account create --name $STORAGE_ACCOUNT_NAME \
                          --resource-group $RESOURCE_GROUP_NAME \
                          --location $LOCATION \
                          --sku Standard_LRS \
                          --kind StorageV2 \
                          --access-tier Hot

# Get the connection string for the storage account
CONNECTION_STRING=$(az storage account show-connection-string -n $STORAGE_ACCOUNT_NAME -g $RESOURCE_GROUP_NAME --query connectionString --output tsv)

# Create a blob container
az storage container create --name $CONTAINER_NAME --connection-string $CONNECTION_STRING

# Create a dummy file for upload
echo "This is a test backup file." > $FILE_TO_UPLOAD

# Upload a file to the blob container
az storage blob upload --container-name $CONTAINER_NAME \
                       --file $FILE_TO_UPLOAD \
                       --name "$FILE_TO_UPLOAD" \
                       --connection-string $CONNECTION_STRING

echo "Storage account '$STORAGE_ACCOUNT_NAME' created and '$FILE_TO_UPLOAD' uploaded to container '$CONTAINER_NAME'."
```

#### 2.2. Azure Disks and Data Protection

Managed Disks simplify VM disk management significantly. Understanding disk types (Standard HDD, Standard SSD, Premium SSD, Ultra Disk) and their performance characteristics is vital for optimizing VM workloads. For data protection, Azure Backup offers a robust, cloud-native solution for VMs, SQL databases, and file shares. Azure Site Recovery provides business continuity by replicating workloads to Azure.

**Practical Tip:** For production VMs, always use Premium SSDs or Ultra Disks. Snapshot disks before major changes. Implement Azure Backup for all critical VMs and databases, and regularly test your recovery procedures.

```powershell
# Get the VM and its OS disk
$resourceGroupName = "my-compute-rg"
$vmName = "my-prod-vm"
$vm = Get-AzVM -ResourceGroupName $resourceGroupName -Name $vmName
$osDisk = Get-AzDisk -ResourceGroupName $resourceGroupName -DiskName $vm.StorageProfile.OsDisk.Name

# Create a snapshot of the OS disk
$snapshotConfig = New-AzSnapshotConfig -OsType Windows -DiskSizeGB $osDisk.DiskSizeGB -Location $osDisk.Location -CreateOption Copy -SourceUri $osDisk.Id
New-AzSnapshot -ResourceGroupName $resourceGroupName -SnapshotName "$($vmName)-OSDisk-Snapshot-$(Get-Date -Format 'yyyyMMddHHmmss')" -Snapshot $snapshotConfig

# Enable Azure Backup for a VM (conceptual, full setup involves a Recovery Services Vault)
# New-AzRecoveryServicesVault -Name "MyBackupVault" -ResourceGroupName $resourceGroupName -Location $osDisk.Location
# Enable-AzVMBackup -ResourceGroupName $resourceGroupName -Name $vmName -VaultId (Get-AzRecoveryServicesVault -Name "MyBackupVault").ID -PolicyName "DefaultPolicy"
```

### 3. Deploying and Managing Azure Compute Resources: The Heart of Your Applications

Compute resources are where your applications run. Azure offers a flexible range from traditional Virtual Machines (VMs) to modern container services and serverless functions. As a sysadmin, you'll spend considerable time provisioning, managing, and optimizing these resources.

#### 3.1. Virtual Machines (VMs)

Deploying, configuring, and managing Windows or Linux VMs in Azure is a core skill. This includes understanding VM sizes, availability options (Availability Sets, Availability Zones), scaling (VM Scale Sets), and connecting to them securely. For administrators familiar with Hyper-V or VMware, the concepts translate well, but the management plane is different.

**Practical Tip:** Always use managed disks. Leverage Availability Zones for high availability across different physical data centers within a region. Use custom VM images for consistent deployments and faster provisioning. Implement auto-shutdown schedules for non-production VMs to save costs.

**Code Example: Deploying a Windows Server VM with Azure CLI**

```azurecli
# Define variables
RESOURCE_GROUP_NAME="my-compute-rg"
LOCATION="eastus"
VM_NAME="myWinServerVM"
ADMIN_USERNAME="randyadmin"
ADMIN_PASSWORD="YourComplexPassword123!" # Replace with a strong password
VNET_NAME="myVNet"
SUBNET_NAME="default"

# Create a resource group if it doesn't exist
az group create --name $RESOURCE_GROUP_NAME --location $LOCATION

# Create a VNet and Subnet (if they don't exist)
az network vnet create --resource-group $RESOURCE_GROUP_NAME \
                       --name $VNET_NAME \
                       --address-prefix 10.0.0.0/16 \
                       --subnet-name $SUBNET_NAME \
                       --subnet-prefix 10.0.0.0/24

# Deploy a Windows Server 2019 Datacenter VM
az vm create --resource-group $RESOURCE_GROUP_NAME \
             --name $VM_NAME \
             --image "MicrosoftWindowsServer:WindowsServer:2019-Datacenter:latest" \
             --admin-username $ADMIN_USERNAME \
             --admin-password $ADMIN_PASSWORD \
             --location $LOCATION \
             --public-ip-sku Standard \
             --vnet-name $VNET_NAME \
             --subnet $SUBNET_NAME \
             --size Standard_DS2_v2 \
             --no-wait # Deploy in the background

echo "VM '$VM_NAME' deployment initiated. It will take a few minutes to complete."
```

#### 3.2. Containerization and Serverless (Briefly)

While AZ-104 primarily focuses on IaaS, an awareness of PaaS compute options like Azure Container Instances (ACI) and Azure Kubernetes Service (AKS) is beneficial. You should also be familiar with Azure Functions for event-driven serverless computing. While deeper management of these falls under other certifications (AZ-204, AZ-305), knowing their place in the Azure ecosystem is crucial for architectural discussions.

### 4. Configuring and Managing Virtual Networking: The Cloud's Central Nervous System

Azure Networking is arguably one of the most complex yet critical domains. It dictates how your resources communicate with each other, with on-premises networks, and with the internet. A deep understanding of VNets, subnets, Network Security Groups (NSGs), routing, DNS, and connectivity options like VPN Gateways and ExpressRoute is non-negotiable for any Azure admin.

#### 4.1. Virtual Networks (VNets) and Network Security Groups (NSGs)

VNets are isolated networks in Azure, providing connectivity for your VMs and other resources. NSGs act as a stateful firewall, controlling inbound and outbound traffic at the subnet or NIC level.

**Practical Tip:** Design your VNets with proper CIDR blocks and subnets from the start. Use NSGs to implement a strong defense-in-depth strategy, placing them both at the subnet level and on individual VM NICs. Prioritize your NSG rules carefully. Avoid giving public IPs to VMs unless absolutely necessary; use Azure Bastion or VPN for secure remote access.

**Code Example: Creating a VNet with multiple subnets and an NSG with Azure CLI**

```azurecli
# Define variables
RESOURCE_GROUP_NAME="my-network-rg"
LOCATION="eastus"
VNET_NAME="ProductionVNet"
APP_SUBNET_NAME="AppSubnet"
DB_SUBNET_NAME="DBSubnet"
NSG_NAME="AppSubnetNSG"

# Create a resource group
az group create --name $RESOURCE_GROUP_NAME --location $LOCATION

# Create the VNet
az network vnet create --resource-group $RESOURCE_GROUP_NAME \
                       --name $VNET_NAME \
                       --address-prefix 10.1.0.0/16 \
                       --location $LOCATION

# Create App Subnet
az network vnet subnet create --resource-group $RESOURCE_GROUP_NAME \
                              --vnet-name $VNET_NAME \
                              --name $APP_SUBNET_NAME \
                              --address-prefix 10.1.1.0/24

# Create DB Subnet
az network vnet subnet create --resource-group $RESOURCE_GROUP_NAME \
                              --vnet-name $VNET_NAME \
                              --name $DB_SUBNET_NAME \
                              --address-prefix 10.1.2.0/24

# Create an NSG for the App Subnet
az network nsg create --resource-group $RESOURCE_GROUP_NAME \
                      --name $NSG_NAME \
                      --location $LOCATION

# Allow RDP from a specific trusted IP
az network nsg rule create --resource-group $RESOURCE_GROUP_NAME \
                           --nsg-name $NSG_NAME \
                           --name "AllowRDPFromTrustedIP" \
                           --priority 100 \
                           --direction Inbound \
                           --source-address-prefixes "YOUR_PUBLIC_IP_ADDRESS/32" \
                           --destination-address-prefixes "*" \
                           --destination-port-ranges 3389 \
                           --protocol Tcp \
                           --access Allow

# Allow HTTP/HTTPS inbound
az network nsg rule create --resource-group $RESOURCE_GROUP_NAME \
                           --nsg-name $NSG_NAME \
                           --name "AllowHttpHttpsInbound" \
                           --priority 110 \
                           --direction Inbound \
                           --source-address-prefixes "Internet" \
                           --destination-address-prefixes "*" \
                           --destination-port-ranges 80 443 \
                           --protocol Tcp \
                           --access Allow

# Allow outbound from App Subnet to DB Subnet
az network nsg rule create --resource-group $RESOURCE_GROUP_NAME \
                           --nsg-name $NSG_NAME \
                           --name "AllowOutboundToDBSubnet" \
                           --priority 120 \
                           --direction Outbound \
                           --source-address-prefixes "10.1.1.0/24" \
                           --destination-address-prefixes "10.1.2.0/24" \
                           --destination-port-ranges "*" \
                           --protocol "*" \
                           --access Allow

# Associate the NSG with the App Subnet
az network vnet subnet update --resource-group $RESOURCE_GROUP_NAME \
                              --vnet-name $VNET_NAME \
                              --name $APP_SUBNET_NAME \
                              --network-security-group $NSG_NAME

echo "VNet '$VNET_NAME' with subnets '$APP_SUBNET_NAME', '$DB_SUBNET_NAME' and NSG '$NSG_NAME' configured."
```

#### 4.2. Inter-VNet Connectivity and Hybrid Networking

For complex environments, VNet Peering allows seamless, low-latency connectivity between VNets within the same or different regions. For hybrid scenarios, Azure VPN Gateway (site-to-site VPN) or ExpressRoute (private, dedicated connection) bridges your on-premises network to Azure, extending your data center into the cloud.

**Practical Tip:** Use VNet Peering for connecting logically separate environments within Azure. For hybrid connectivity, evaluate VPN Gateway for simplicity and cost-effectiveness for smaller workloads, and ExpressRoute for mission-critical, high-bandwidth, low-latency requirements.

### 5. Monitoring and Backing Up Azure Resources: Ensuring Resilience and Visibility

You can't manage what you can't see, and you can't protect what you don't back up. Azure Monitor provides a unified platform for collecting, analyzing, and acting on telemetry data from your Azure and on-premises resources. Azure Backup and Azure Site Recovery are your weapons against data loss and service disruption.

#### 5.1. Azure Monitor and Log Analytics

Azure Monitor collects metrics and logs from virtually all Azure services. Log Analytics Workspace is your central repository for these logs, enabling powerful querying and analysis (Kusto Query Language - KQL). This is invaluable for troubleshooting, performance optimization, and security auditing.

**Practical Tip:** Configure diagnostic settings for *all* critical resources to send logs and metrics to a Log Analytics Workspace. Learn KQL; it's a powerful tool for quickly finding insights from vast amounts of log data. Set up proactive alerts for critical metrics (e.g., high CPU, low disk space, network latency spikes) and security events.

**Code Example: Configuring Diagnostic Settings for a VM to send logs to Log Analytics**

```azurecli
# Define variables
RESOURCE_GROUP_NAME="my-compute-rg"
VM_NAME="myWinServerVM"
LOG_ANALYTICS_WORKSPACE_NAME="myLAWorkspace$(head /dev/urandom | tr -dc a-z0-9 | head -c 8)" # Ensure unique
LOCATION="eastus"

# Create a Log Analytics Workspace
az monitor log-analytics workspace create --resource-group $RESOURCE_GROUP_NAME \
                                         --workspace-name $LOG_ANALYTICS_WORKSPACE_NAME \
                                         --location $LOCATION

# Get the Log Analytics Workspace ID
LA_WORKSPACE_ID=$(az monitor log-analytics workspace show --resource-group $RESOURCE_GROUP_NAME \
                                                           --workspace-name $LOG_ANALYTICS_WORKSPACE_NAME \
                                                           --query id --output tsv)

# Get the VM ID
VM_ID=$(az vm show --resource-group $RESOURCE_GROUP_NAME \
                   --name $VM_NAME \
                   --query id --output tsv)

# Enable Azure Monitor VM Insights (installs necessary agents and configures diagnostic settings)
az vm extension set --resource-group $RESOURCE_GROUP_NAME \
                    --vm-name $VM_NAME \
                    --name "MicrosoftMonitoringAgent" \
                    --publisher "Microsoft.EnterpriseCloud.Monitoring" \
                    --protected-settings "{\"workspaceKey\": \"$(az monitor log-analytics workspace get-shared-keys --resource-group $RESOURCE_GROUP_NAME --workspace-name $LOG_ANALYTICS_WORKSPACE_NAME --query primarySharedKey --output tsv)\"}" \
                    --settings "{\"workspaceId\": \"$(az monitor log-analytics workspace show --resource-group $RESOURCE_GROUP_NAME --workspace-name $LOG_ANALYTICS_WORKSPACE_NAME --query customerId --output tsv)\"}"
```

#### 5.2. Azure Backup and Site Recovery

Azure Backup provides cloud-based backup and restore services. It's an essential component of your business continuity and disaster recovery (BCDR) strategy. Azure Site Recovery extends this by offering near real-time replication and orchestrated failover for VMs and physical servers, both to and within Azure.

**Practical Tip:** Implement a 3-2-1 backup strategy leveraging Azure Backup. Regularly perform test restores to ensure data integrity and validate your recovery procedures. For critical applications requiring low RTO/RPO, use Azure Site Recovery.

### Real-World Application: Securing and Migrating a Legacy Application to Azure

Consider a common scenario: an organization needs to migrate a critical, multi-tier legacy application from an on-premises data center to Azure, while simultaneously improving its security posture and ensuring high availability.

1. **Identity Integration:** First, we'd establish hybrid identity by configuring Azure AD Connect, synchronizing on-premises user accounts to Azure AD. Conditional Access policies would be set up to enforce MFA for administrative access and to restrict access to the application based on corporate network location or compliant devices. RBAC would be used to grant least-privilege access to development and operations teams on specific resource groups.
2. **Network Architecture:** We'd design a Hub-Spoke VNet architecture. The Hub VNet would host shared services like a VPN Gateway (for site-to-site connectivity to on-premises) and Azure Firewall. Spoke VNets would be created for the application (e.g., one for web tier, one for application tier, one for database tier). NSGs would be meticulously configured on each subnet to allow only necessary traffic flows (e.g., web tier to application tier on specific ports, application tier to database tier).
3. **Compute and Storage Migration:**
   - **Database:** Migrate the on-premises SQL Server database to Azure SQL Database or a SQL Server on an Azure VM, depending on complexity and compatibility. If using a VM, use Premium SSDs and configure Azure Backup.
   - **Application Servers:** Create custom VM images from the on-premises application servers. Deploy these VMs into the application subnet, placing them in an Availability Set (or across Availability Zones for higher resilience). Use VM Extensions to automate post-deployment configuration, such as joining a domain or installing application components.
   - **Storage:** If the application requires shared file storage, migrate it to Azure Files and potentially use Azure File Sync to keep it in sync with on-premises if hybrid access is needed during migration.
4. **Monitoring and Disaster Recovery:**
   - **Monitoring:** Configure Azure Monitor and Log Analytics Workspace to collect performance metrics, application logs, and security events from all migrated resources. Set up alerts for high CPU, low disk space, failed logins, and application errors.
   - **Backup & DR:** Implement Azure Backup for all VMs and Azure SQL Databases. For the most critical application VMs, configure Azure Site Recovery to another Azure region for full regional disaster recovery with low RTO/RPO.

This comprehensive approach, leveraging the skills validated by AZ-104, transforms a risky migration into a structured, secure, and resilient cloud deployment.

### Best Practices and Lessons Learned from a Decade in IT

Passing AZ-104 is a great step, but truly mastering Azure administration comes from applying principles and lessons learned over years of managing complex systems:

1. **Automate Everything You Can (Safely):** Manual processes are error-prone and time-consuming. Leverage Azure CLI, Azure PowerShell, ARM templates, Bicep, or Terraform for Infrastructure as Code (IaC).
   > "If you do it more than twice, script it."
2. **Cost Management is an Ongoing Task:** Azure offers immense power, but with great power comes great cloud bills. Regularly review your resources, use resource tagging for cost allocation, implement shutdown schedules for non-production environments, and explore Azure Reserved Instances or Azure Hybrid Benefit.
3. **Security First, Always:** Adopt a "assume breach" mentality. Implement multi-factor authentication, principle of least privilege, network segmentation with NSGs/Azure Firewall, and regularly review security recommendations from Azure Security Center (now Defender for Cloud).
4. **Monitor Proactively, Not Reactively:** Don't wait for users to report issues. Set up comprehensive monitoring and alerting. Understand your baseline performance and define thresholds for alerts.
5. **Documentation is Not Optional:** Cloud environments are dynamic. Document your VNet designs, RBAC assignments, automation scripts, and deployment procedures. This is crucial for team collaboration and operational continuity.
6. **Continuous Learning is Your Superpower:** The cloud evolves at an incredible pace. What's current today might be legacy tomorrow. Stay curious, follow Azure updates, and dedicate time to hands-on experimentation.
7. **Test, Test, Test:** Whether it's a new deployment, a backup strategy, or a disaster recovery plan – test it thoroughly and regularly. Don't assume it works until you've proven it.
8. **Understand the Shared Responsibility Model:** Microsoft manages the security *of* the cloud; you are responsible for security *in* the cloud. Know where that line is.
